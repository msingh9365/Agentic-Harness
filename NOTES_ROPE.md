**Context (stored, from branch `cpu-order-tests`, `results/order_tests/README.md`).** M3 (ATT+bal, corrected tokenizer, 10 seeds) loses 4.0 pAUC points under the window-preserving shuffle (RESOLVED) and at most 2.1 points under prepended shifts of about 8 to 64 tokens; M1 loses 26.9 and up to 35 points. The question here: if the absolute sinusoidal position code is replaced by a RELATIVE code, does the model use the order of the calls more, while staying robust to absolute shifts and padding?

## 1. Variants (all are M3: attention pooling, balanced padding p 0.5, corrected tokenizer `bpe50k_fix`, same data, same padding pool and stream, seeds 0 to 9, all 75,298 January reports)
M3's architecture (`baseline/pe.py`, authors' `TransformerEncoderChunks`): embedding 64 x sqrt(64), sinusoidal position code added at the input (global position 0..511, paper mode), dropout 0.3, 2 pre-norm Transformer layers (8 heads, d_h = 8, feed-forward 256), self-attention inside 64-token blocks, attention pooling over the real tokens (id != 0), head 64 -> 1.
- **V0 "M3 ATT+bal"**: M3 as is. The stored final weights and April logits (`gs-fix-w-m3`, seeds 0 to 9) are reused; nothing is retrained. Its order-test scores are the stored ones of branch `cpu-order-tests` (same code and seeds); its attack scores are recomputed from the stored weights in the same kernel as those of V1 to V3 (only so that cluster intervals can be formed).
- **V1 "M3 + RoPE (blocks)"**: NO sinusoidal code at the input (embedding x sqrt(64), then the same dropout); in every attention layer the queries and keys are rotated (RoPE, Su et al.): head dimension 8 = 4 frequency pairs, adjacent pairing (x_2i, x_2i+1), inverse frequencies 10000^(-2i/8) for i = 0..3, position = token index within the 512 window (the global index 64c + j of the token in block c; inside a block only differences matter). Attention stays inside the 64-token blocks.
- **V2 "M3 + RoPE (full)"**: as V1 but ONE attention over all 512 positions (no blocks).
- **V3 "M3 + full attention"** (control): the sinusoidal input code as M3 (global positions) with FULL 512 attention. V3 separates the effect of full attention from the effect of RoPE.
RoPE adds no parameter. The new layers reuse the parameters of `torch.nn.TransformerEncoderLayer` (same names and shapes; the forward pass is replaced), so V1 to V3 have the same state-dict keys and the same initial weights as M3 for the same seed. Padding positions get their position (no key mask), as in M3. Dropout 0.3 on the embedding, attention probabilities, sub-layer outputs and feed-forward as in M3.

## 2. Recipe, guard and training
Recipe of V1 to V3 = the final M3 recipe: lr 1e-3, 3 epochs, batch 96, AdamW weight decay 1e-2, gradient clip 0.5, dropout 0.3, balanced padding (p 0.5, k ~ U{1..50}, insert or prepend 50/50, replace, malware and benign alike, random stream 7000, padding pool = the 21,507 benign reports of the group-split training part), all 75,298 January reports, April logits and weights stored after epoch 3 only (not opened until the evaluation of section 4). Commands: the `gs_grid --family attbal --fix --epochs-override 3` runs of `baseline/gs_grid.py` with the model replaced by the variant (wrapper `results/rope_test/launcher.py` replaces `pe.build_chunks`; every other line of training is the unmodified `baseline/v2pe.py`).
**Validation guard (before the final runs; January fold 9 = the group-split slice, 8,718 validation reports, training on its 66,580 training reports, NO April file is opened or read; the epoch-study mode `--study-fold 9`, 3 seeds 0 to 2, 3 epochs, per-epoch validation metrics).** A variant "collapses" if the validation AUC of any of its 3 seeds is below 0.8 after epoch 3, and "diverges" if its mean validation loss after epoch 3 is above 3 times the mean validation loss of M3 on the same fold and epoch (stored epoch study: `results/groupsplit/epoch_study/`, M3 fold 9, seeds 0 to 4) or is NaN. A variant that collapses or diverges is retried ONCE with lr 5e-4 (same guard) and the retry's setting is used for ALL its 10 seeds; the retry is recorded. If it fails again, the item stops (`STOP.txt`) and that variant is "not run". No other tuning of any kind; the guard numbers are also reported (validation, fold 9; not an April number).

## 3. Implementation checks before any training (unit tests in `results/rope_test/test_rope.py`, committed before training)
(a) RoPE relative property: for random q and k, the score q_i . k_j after rotation is unchanged when both positions are shifted by the same offset (maximum difference < 1e-5); (b) the V1 class with RoPE disabled and the input code restored reproduces the forward pass of the unmodified M3 model (same weights, fixed batch of real April tokens, eval mode): maximum logit difference < 1e-5; also the V3 class with its 512 attention split back into blocks by a mask equals (b) (checks the full-attention path); (c) the parameter count of V1, V2, V3 equals that of M3 (the exact counts are printed and written to `results/rope_test/param_counts.json`); (d) V1 to V3 for seed s have the same initial state dict as M3 for seed s (same shapes, same random stream); (e) a short CPU training run (50 batches) of each variant gives a finite, falling loss. Any failed test stops the item.

## 4. Evaluation (ONE April opening for V1 to V3 together, after their training results are committed; no April number of V1 to V3 is read before that; V0 data are the stored ones)
All with the 10 seeds of each variant, April, 17,402 reports. Primary metric pAUC@1e-2 NORMALISED (area up to FPR 0.01 / 0.01, `baseline/common.py`).
1. **Clean:** pAUC@1e-2, TPR@1e-3, TPR@1e-2, AUC, F1 at logit 0 (the project's `binary_metrics`); seen / unseen split by whether the report's API sequence (`hash_apis`) occurs in the January training slice (as P2, `gs_seen_unseen.py` definition).
2. **Shuffle test of NOTES_ORDER** (window-preserving shuffle, local shuffle in groups of 5, reversal, reference full shuffle): the code, seeds (`[8100, row, variant]`) and checks of `results/order_tests/order_tests.py` of branch `cpu-order-tests` (copied to `results/rope_test/order/`; only the model loader is replaced), window 512, clean = rebuilt from the call store.
3. **Shift test of NOTES_ORDER** (nested benign-call prepends, targets 0, 8, ..., 64 tokens, exact s recorded; control set at target 32): same code and seeds (`[8200, row]`, `[8300, row, j]`).
4. **Attacks as Stage J** (`baseline/gs_attack.py` with its edit builder, the ranking `ranking_gs.json` of Stage H, EVAL pool = the 3,161 group-split validation benign reports): random prepend k 5, 20, 50, 100, 200 and insert k 5, 20, 50, 100, 200, LightGBM prepend and insert k 20, 50, 100 (all 17 Stage J sets, of which the ones asked for are random 20/50/100 prepend, 50/200 insert, LightGBM 50 prepend and insert), detection of malware at the clean 1% and 0.1% FPR thresholds of each model and seed, padded-benign FPR; **white-box** greedy (500 April malware, 200 candidates per step, prepend, 50 steps) for **V1 and V2 only, seeds 0, 1, 2**, detection after 20 and 50 steps. Every attack job asserts that its unedited scores reproduce the stored April logits of the model (tolerance 2e-3).
5. **Contrasts V1-V0, V2-V0, V3-V0, V2-V3** for the clean pAUC@1e-2 and for the criteria of section 5, with the cluster bootstrap over the 2,509 April `hash_apis` groups (cells = group x class, 1,000 resamples, numpy seed 0, same resample for all variants, per resample the metric of every seed, thresholds recomputed on the resample's clean benign scores for threshold-based numbers, mean over the seeds), and the number of seeds going each way (paired by index only). **Resolved = the cluster 95% interval excludes 0** (the stricter "7 of 10 seeds" rule of NOTES 26 is not used here; the seed counts are shown next to every number).

## 5. Decision rule (fixed now)
A variant is **"order-aware and position-robust"** if ALL four hold (each is reported met / not met per variant; the contrast is always against V0 = M3):
(i) the window-shuffle drop (pAUC clean minus window shuffle) is >= 5 points AND resolved (its cluster 95% interval excludes 0) (M3: 4.0);
(ii) the largest drop of pAUC over the shifts 8 to 64 tokens (against shift 0) is <= 2 points AND not resolved (its cluster 95% interval contains 0) (M3: 2.1, so M3 itself does not meet it);
(iii) the detection under LightGBM 50 prepend (share of April malware above the clean 1% FPR threshold, mean over seeds) is NOT resolved worse than that of M3 (the cluster interval of V - V0 does not lie wholly below 0);
(iv) the clean pAUC@1e-2 is NOT resolved worse than that of M3 (the cluster interval of V - V0 does not lie wholly below 0).
If no variant meets all four, the README says so plainly. The remaining measures (other attacks, white-box, AUC, TPR, seen/unseen, logit changes) are descriptive and cannot change the verdict. Whether a drop under the shuffle comes from order or from absolute position is not separated by these tests (stated in the README).
